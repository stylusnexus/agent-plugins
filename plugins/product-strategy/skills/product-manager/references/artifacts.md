# Create, inspect, and review artifacts

Create the requested project-specific artifact, not just a description or an empty template. Use the smallest useful set of editable source, rendered output, and underlying evidence/data. Keep source and outputs in the project, and retain user changes.

## Workflow
1. Establish audience, decision, requested format, and existing source. Read the relevant PM workflow and supporting evidence; draft with labelled unknowns.
2. For diagrams use [pm-visuals](../../pm-visuals/SKILL.md). For documents, slides, spreadsheets, and PDF use available host format tools/skills. Do not claim native tracked changes, spreadsheet formulas, or exports you have not created and checked.
3. For standalone HTML use the host html skill, or the `html` skill from the `reporting-comms` plugin when installed. Keep content offline, accessible, responsive, and printable with editable source and evidence references. External hyperlinks are fine; remote dependencies are not.
4. Inspect the rendered artifact with the host browser/computer tool when available. Check text clipping, hierarchy, source labels, actual values, navigation, and useful mobile/print behavior. Report untested formats or unavailable tools honestly. Do not equate markup validation with a visual check.
5. When a person wants to mark up wording or judge a draft, use their project-local redline skill first, then host redline, then the `redline` skill from the `reporting-comms` plugin. Make an adjacent `.redline.html` with named blocks and source attribution. Script-generated visuals use comment-only review. Keep original source until feedback is returned.
6. Explain that Send downloads a local `.redline.md`; it does not send to anyone. Read the returned review, preserve exact human edits, apply anchored comments to the source, and regenerate the presentation. Surface conflicting or stale anchors rather than guessing. Keep review records unless the user asks to discard them.
7. If the user asks for an editorial redline rather than browser markup, provide anchored before/after changes, rationale, and a revised draft. Distinguish agent suggestions from accepted human edits. Native DOCX tracked changes require actual format support; an HTML comparison is not that feature.

Browser publishing, outreach, spend, deployment, and external document writes require applicable authorization. Local artifact creation and inspection are part of the requested workflow. An unavailable browser does not prevent delivering the local artifact and a precise verification limit.
