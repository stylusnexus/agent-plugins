# A PRD as an evolving decision brief

Source: Paweł Huryn, *How to Write a Product Requirements Document? The Best PRD Template.*, March 9, 2024. Source originals are not included; use the bundled guidance and Markdown worksheets.

Use the [initiative brief](../templates/initiative-prd.md) for work large or uncertain enough to benefit from shared context. Start during discovery when useful; update the problem, evidence and recommendation as learning changes them. Product, design and engineering collaborate. Discuss consequential choices with stakeholders rather than assuming a circulated document creates agreement.

Retain outcomes and strategic context while progressively adding the solution detail needed for implementation. Link experiments, prototypes and detailed requirements instead of copying them. Keep a clear current source of truth and supersede stale assumptions when implementation or release learning changes the decision. Rejection or substantial reframing is a legitimate result.

Use proportional detail. The author's short-document preference is a useful default, not a hard page limit. Do not adopt absolute bans on user stories, specifications, exact dates or updating after implementation starts: acceptance needs, commitments and the project's workflow govern. Distinguish dates already committed from estimates.

Link separate launch, sales, support and training materials when they exist; otherwise preserve the relevant readiness decisions in the brief instead of leaving a gap because there is no marketing specialist. Avoid duplicate documents. For new products, include business-model assumptions when useful without demanding another canvas.

For a novice, explain each section's purpose and draft from existing evidence. For a direct drafting request, produce the concise brief with labelled unknowns. Use the suite's artifact/redline workflow for reviewable output.
